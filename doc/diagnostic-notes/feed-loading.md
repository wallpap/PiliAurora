# 首页加载排查

2026-10-30 的源码调查发现，推荐首屏耗时可能分布在黑名单同步、内容请求、合作作者补查、过滤发布、视口补位及图片加载等阶段。应为每一段计时，并记录请求返回数量、过滤后数量和首屏可见数量，避免仅凭总耗时判断网络或图片是瓶颈。

当时的实现中，完整黑名单同步发生在内容请求前；启用合作作者检查且需要补查时，一批内容要等补查完成才发布。推荐 App 路径与 Web 路径使用不同参数，应分别核查服务端行为。首屏补位还要区分过滤删除数量与视口容量不足。

调查提出并行启动同步和内容请求、在发布前完成过滤的方向，并建议保留账号隔离及旧请求失效语义。服务端并发页码语义、用户配置和各阶段耗时仍需实测。

当前首页控制器已按视口补足内容，并行启动黑名单同步与推荐下载；普通卡片先展示，待检查的合作视频显示占位。App 推荐按顺序请求，Web 首包之后最多并行下载两页。刷新和账号变化会使旧查询失效。具体行为见[信息流黑名单屏蔽](../guides/content-filtering.md)。
