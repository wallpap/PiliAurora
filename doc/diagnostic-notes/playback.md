# 播放与直播排障

## 视频继续播放但音频消失

2026-10-29 的 Windows 案例中，外部 AAC 音轨的网络读取终止后，剩余音频缓存仍健康了一段时间。旧恢复逻辑在约 30 秒后停止观察；缓存随后耗尽时没有新的错误日志，视频仍可继续播放，整体 buffering 也可能为 false。缓存内小幅 seek 未必产生新的音轨请求。

排查时分别核对视频位置、音频时间、音轨选择、网络错误与缓存状态，覆盖错误后长时间仍有缓存的情况。受控 RST 实验中，缓存内跳转未恢复音频，`audio-reload` 发起新请求后音频时钟恢复。生产类回归覆盖了长缓存后失声及重连期间再次出错。原生实验使用空音频输出，故障注入入口为 `tool/probes/playback/native_audio_stream_recovery.py`。

## 直播退出等待

2026-10-26 的 Windows 主机探针发现，持续到来的渲染更新可能让单个渲染任务一直占据队列，延迟执行输出代次撤销。原实现处理完 64 次持续更新才执行撤销；修复后的渲染任务让出队列，撤销在第一次渲染后执行。探针使用生产渲染类和线程池，GPU 与 mpv 使用桩。长时间观看后的实际挂起仍需设备复现。

复现时记录退出入口、平台和最后完成的关闭阶段，沿 Session、Player 停止、卸载回执、输出释放逐段检查。Windows 同时观察渲染队列是否持续繁忙；Android 结合 Surface、MediaCodec 和线程堆栈判断。关闭超时只说明调用已结算，不能证明原生资源已经释放。

另一次 Windows 返回卡住发生在最大化窗口最小化后恢复：系统发送 `maximize`，旧逻辑却只在 `restore` 时清除最小化标记。根 `TickerMode` 因此保持关闭，返回动画无法结束，图片监听也未恢复。修复让最大化事件走同一恢复流程，并用窗口事件代次隔离迟到的初始化结果。排查返回卡住时，先确认路由动画是否仍在运行，再判断是否已经进入播放器释放阶段。

Android Surface 重建的故障注入还暴露了资源所有权问题：旧 JNI 引用释放失败时应停止重建；新 Surface 和引用完整创建后才登记，创建失败则回滚。释放失败的引用要保留给后续清理，不能先丢失其所有权。对应主机探针位于 `tool/probes/android/`。

## Windows 更新退出

更新时应绕过托盘驻留，先保存播放进度并释放主窗口和播放小窗，再关闭 Hive，最后交由安装器替换文件。2026-10-28 的隔离 Debug 验证覆盖播放、暂停、托盘、多窗口和异常进程等 17 个场景，均完成更新；正常播放场景可重新打开 Hive 读到进度。强制结束卡死进程只能保证退出和释放文件，不能保证最后的播放进度已保存。

## 黑闪及历史日志核对

2026-10-27 的直播黑闪反馈未在本机复现。历史包混合多个版本、会话和重复切片，且缺少反馈时段。检查发现，同一 Player 和纹理可以跨媒体重开复用；`surfaceGeneration` 是应用调度代次，单凭递增不能证明纹理重新分配。点播与直播的码率样本也不能拼成一个会话的画质切换序列。

后续采集先对齐故障时刻、会话、版本、运行程序路径及纹理身份，再核对解码、呈现和网络。使用全新目录与缓存做单变量对照时，先备份用户数据。

## Windows 超分切换

2026-10-14 的固定 mpv 实验中，视频输出重建与长 GOP 解码状态有关。调整重建后的 seek 执行时机后，旧 DLL 在故障注入下失败，新 DLL 通过重建、seek 和硬解检查；Flutter 纹理探针也通过八次重建。测试使用本机 AMD GPU 和 `ao=null`；实际音频输出、其他平台及直播需要另行验证。排查类似问题应同时观察解码错误、实际硬解后端、有效纹理、音频时间线和播放意图。
